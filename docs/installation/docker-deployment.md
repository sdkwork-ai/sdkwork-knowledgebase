# Docker Deployment (Standalone Container)

This guide covers building and running the sdkwork-knowledgebase **standalone
container image** (`runtimeTarget = "container"`, `deploymentProfile =
"standalone"`). The image is a single application unit: it ships the gateway
and worker release binaries, the PC portal bundle, and the federated database
modules, and the docker compose composition brings up the gateway, the
outbox/ingestion worker, PostgreSQL 16 and Redis 7.

For the cloud orchestration layout (Kubernetes), see
`deployments/kubernetes/`. For the host package layout, see
`deployments/README.md`.

## 1. Dependency inventory

### 1.1 Inside the image (release artifacts)

| Item | Path in image | Source | Notes |
| --- | --- | --- | --- |
| Standalone gateway binary | `/opt/sdkwork/knowledgebase/bin/sdkwork-api-knowledgebase-standalone-gateway` | `target/release/...` | Main process; serves app/backend/open/internal API surfaces + `/healthz` `/readyz` `/livez` `/metrics` `/openapi.json` on `0.0.0.0:18081` |
| Worker binary | `/opt/sdkwork/knowledgebase/bin/sdkwork-knowledgebase-worker` | `target/release/...` | Outbox + ingestion maintenance; compose `worker` service overrides the entrypoint |
| Entrypoint | `/opt/sdkwork/knowledgebase/container/entrypoint` | generated by `scripts/build-knowledgebase-container.mjs` | `exec gateway "$@"` (database baseline/migrations run in-process) |
| Portal SPA (dist) | `/opt/sdkwork/knowledgebase/portal/dist` | `apps/sdkwork-knowledgebase-pc/dist` (built with `--mode standalone.docker`) | served by the deployment nginx as static SPA; same-origin API paths |
| App identity | `/opt/sdkwork/knowledgebase/sdkwork.app.config.json` | repository root | IAM tenant provisioning (`SDKWORK_APP_ROOT`) |
| Knowledgebase database module | `/opt/sdkwork/knowledgebase/database-modules/sdkwork-knowledgebase/database` | `database/` | `SDKWORK_KNOWLEDGEBASE_APP_ROOT` |
| IAM database module | `/opt/sdkwork/knowledgebase/database-modules/sdkwork-iam/{database,iam}` | `../sdkwork-iam/` | `SDKWORK_IAM_APP_ROOT` |
| Drive database module | `/opt/sdkwork/knowledgebase/database-modules/sdkwork-drive/database` | `../sdkwork-drive/database` | `SDKWORK_DRIVE_APP_ROOT` |
| Web framework module | `/opt/sdkwork/knowledgebase/database-modules/sdkwork-web-framework/database` | `../sdkwork-web-framework/database` | `SDKWORK_WEB_STORE_APP_ROOT` |
| Install manifest | `/opt/sdkwork/knowledgebase/install-manifest.json` | generated | release evidence (file list + sha256) |
| Runtime libs | system | `debian:bookworm-slim` + `libssl3` + `ca-certificates` + `curl` | TLS + healthchecks |

The committed `Dockerfile` at the repository root is the build input for
`pnpm build:container`. The image contains **no source, no node_modules, no
cargo target** — binaries are stripped during staging (PACKAGING_SPEC §3).

### 1.2 External services (never baked into the image)

| Dependency | Version | Compose service | Notes |
| --- | --- | --- | --- |
| PostgreSQL | 16 | `postgres` | Required; connection via `SDKWORK_DATABASE_*` env; schema baseline applied on startup (`SDKWORK_DATABASE_AUTO_MIGRATE=1`) |
| Redis | 7 | `redis` | Optional in `development` posture, required for `staging`/`production`; connection via `SDKWORK_KNOWLEDGEBASE_REDIS_*` |

### 1.3 Runtime posture

The compose defaults run the gateway in **explicit development mode**
(`SDKWORK_KNOWLEDGEBASE_ENVIRONMENT=development`): no IM RPC cluster or Redis
hardening is required, and the IAM resolver accepts the gateway-issued
bootstrap Access-Token for the credential-entry login flow (the same posture
sdkwork-cloudrouter uses for its local container deployments). A `staging` /
`production` posture additionally requires Redis, all
`SDKWORK_KNOWLEDGEBASE_IM_RPC_*` keys, and strong secrets — see
`etc/topology/standalone.production.env` for the required key set.

## 2. Port plan (never collides with `pnpm dev`)

`pnpm dev` listens on **18081** (Rust gateway) and **5184** (Vite dev server).
The container listens on **18081 inside its own network namespace** and is
published on the host as **3904**, free of every workspace port.

| Host port | Container port | Owner |
| --- | --- | --- |
| 3904 | 18081 | api container (compose default) |
| — (compose network only) | 5432 | postgres |
| — (compose network only) | 6379 | redis |
| — (compose network only) | 18085 | worker health |

Ports deliberately avoided on the host: 18081 (dev gateway), 5184 (dev vite),
3900 (platform gateway), 5432/15432 (dev/test PostgreSQL), 6379 (dev Redis),
80/443 (nginx).

## 3. Build

Prerequisites: Linux or WSL host (Linux binaries), Docker daemon running, and
the release build products:

```bash
cargo build --release -p sdkwork-api-knowledgebase-standalone-gateway -p sdkwork-knowledgebase-worker
pnpm --dir apps/sdkwork-knowledgebase-pc exec vite build --mode standalone.docker   # if dist/ is stale
```

Then build the image:

```bash
pnpm build:container            # docker build -f Dockerfile -t sdkwork-knowledgebase:local
pnpm build:container:check      # validate the plan without building
```

The build assembles `dist/install-package-staging/` (stripped binaries, portal
dist, federated database modules, app config, entrypoint, install manifest),
produces the container install package
(`dist/install-packages/sdkwork-knowledgebase-linux-x64-container-<version>.tar.gz`),
unpacks it into `dist/container-image-build/`, runs `docker build`, and
records the immutable image evidence in `dist/container-image.json`:

```json
{
  "schemaVersion": "2026-08-08.container-image.v1",
  "packageId": "linux-x64-container",
  "version": "0.1.0",
  "imageTag": "sdkwork-knowledgebase:local",
  "packageArchiveSha256": "...",
  "repoDigest": null,
  "imageId": "sha256:...",
  "buildDate": "..."
}
```

The `imageId`/`repoDigest` are the immutable image digests; mutable tags are
convenience labels, not release identity (RELEASE_SPEC §4.1).

### 3.1 Fast rebuilds (input snapshot cache)

Every build input (release binaries, portal dist, federated database modules,
app config) is snapshotted in `dist/container-image-staging.snapshot.json`.
When nothing changed, the packaging pipeline (staging copy, install package
archive, unpack) is skipped and only `docker build` runs against the cached
context:

```bash
pnpm build:container        # inputs unchanged: seconds
pnpm build:container -- --force   # bypass the cache and rebuild everything
```

After the image exists, everyday deployment is a single command:

```bash
docker compose up -d        # start/update the stack (seconds)
```

## 4. WSL quick deployment (Windows host + WSL Ubuntu)

The one-command orchestration `pnpm deploy:docker:wsl` runs the whole pipeline
inside WSL Ubuntu (invoked from Windows):

```bash
pnpm deploy:docker:wsl              # full pipeline (long on first run)
pnpm deploy:docker:wsl -- --verify-only     # re-verify a running stack
pnpm deploy:docker:wsl -- --no-cargo --no-frontend   # iterate after first build
```

What it does (idempotent stages, see `scripts/wsl-deploy.sh`):

1. **Preflight** — installs `docker.io` + compose plugin, `nginx`, `rsync`
   via apt when missing and starts the docker daemon.
2. **Workspace sync** — copies the workspace (knowledgebase + the sibling
   repositories required by cargo path deps and the pnpm workspace) from the
   Windows filesystem (`/mnt/<drive>/sdkwork-space`) to the WSL ext4
   filesystem (`~/sdkwork-workspace`, excludes `target/`, `node_modules/`,
   `dist/`, `.git/`...). Builds run on ext4 because 9p mounts are too slow for
   cargo/vite.
3. **Rust build** — installs rustup if missing and runs
   `cargo build --release -p sdkwork-api-knowledgebase-standalone-gateway -p
   sdkwork-knowledgebase-worker` (first build takes a while; afterwards
   incremental).
4. **Portal build** — installs Node 22 and the pnpm package manager when missing, runs `pnpm install`, then
   `vite build --mode standalone.docker` (same-origin API profile).
5. **Image build** — `pnpm build:container` (stage 3 of this guide).
6. **Compose up** — copies `docker/.env.example` to `.env` when missing and
   runs `docker compose up -d`, then waits for `/readyz`.
7. **Nginx + hosts** — copies the portal dist to
   `/opt/sdkwork/knowledgebase/portal`, installs
   `docker/nginx/testapikb-knowledgebase.conf` under
   `/etc/nginx/sites-enabled/sdkwork/`, reloads nginx, and appends the three
   test domains to the Windows `hosts` file (falls back to printed elevated
   instructions when not writable).
8. **Verification** — compose ps, gateway probes, portal and API plane
   smoke checks.

### 4.1 Domain chain

```
Windows browser -> hosts: 127.0.0.1 testapikb.sdkwork.com testapikb.birdcoder.com testapikb.dtupay.com
-> Windows localhost:80 -> WSL nginx :80 (server_name: the three domains)
-> static: /opt/sdkwork/knowledgebase/portal (SPA fallback /index.html)
-> API:   /app/v3/api/* /backend/v3/api/* /knowledge/v3/api/* /internal/v3/api/* -> http://127.0.0.1:3904
-> probes: /healthz /readyz /livez /openapi.json -> http://127.0.0.1:3904
```

The portal build uses **same-origin** API URLs
(`VITE_SDKWORK_KNOWLEDGEBASE_DEV_SAME_ORIGIN_API=true` in
`.env.standalone.docker`), so the browser talks to nginx only and the real
domain is preserved end to end. If the machine uses a system HTTP proxy (e.g.
Clash), add these domains to the proxy bypass/直连 list or temporarily disable
the proxy — otherwise the proxy resolves the domains instead of the local
hosts entry.

## 5. Run (docker compose, recommended)

```bash
pnpm build:container
docker compose up -d
```

Services: `api` (host port `3904:18081`), `worker`, `postgres`, `redis`
(compose network only). Override credentials and tunables with a `.env` file
next to `docker-compose.yml` (copy `docker/.env.example`).

### 5.1 Change configuration at deployment time

Two channels, in increasing precedence (ENVIRONMENT_SPEC §11):

1. **Environment file** — copy `docker/.env.example` to the repository root as
   `.env` and adjust values; docker compose reads it automatically:
   ```bash
   cp docker/.env.example .env
   docker compose up -d
   ```
   `RUST_LOG` (default `info`) controls log verbosity. PostgreSQL/Redis hosts
   can point at managed services via `KNOWLEDGEBASE_POSTGRES_HOST` /
   `KNOWLEDGEBASE_REDIS_HOST`.
2. **Secret files** — production should mount secrets and reference them with
   the `_FILE` environment variants (`SDKWORK_KNOWLEDGEBASE_SECRETS_ENCRYPTION_KEY_FILE`,
   `SDKWORK_IAM_TENANT_SIGNING_MASTER_SECRET_FILE`) instead of env values.
   Environment values always override, and nothing is baked into the image.

### 5.2 Concurrency and performance tuning

| Variable | Default | Meaning |
| --- | --- | --- |
| `KNOWLEDGEBASE_DATABASE_MAX_CONNECTIONS` | 30 | PostgreSQL app pool ceiling |
| `KNOWLEDGEBASE_DATABASE_MIN_CONNECTIONS` | 5 | Warm connections kept ready |
| `PG_MAX_CONNECTIONS` | 200 | PostgreSQL server-side ceiling |
| `KNOWLEDGEBASE_CPU_LIMIT` / `KNOWLEDGEBASE_MEMORY_LIMIT` | 4.0 / 4g | api deploy limits |
| `KNOWLEDGEBASE_WORKER_CPU_LIMIT` / `KNOWLEDGEBASE_WORKER_MEMORY_LIMIT` | 2.0 / 2g | worker deploy limits |

Pool size rule of thumb: ~CPU cores × 4, capped; keep `PG_MAX_CONNECTIONS`
comfortably above the pool.

## 6. Verify

```bash
curl -fsS http://127.0.0.1:3904/healthz      # liveness
curl -fsS http://127.0.0.1:3904/readyz       # readiness (DB + Redis + Drive)
curl -fsS http://127.0.0.1:3904/openapi.json # API contract
docker compose ps                            # all services healthy
ss -tlnp | grep 3904                         # host: only 3904 served by the container
```

### 6.1 Multiple domain names on port 80 (localhost hosts mapping)

1. Map the domains in `C:\Windows\System32\drivers\etc\hosts`:
   ```
   127.0.0.1 testapikb.sdkwork.com testapikb.birdcoder.com testapikb.dtupay.com
   ```
2. The deployment nginx site (kept in
   `docker/nginx/testapikb-knowledgebase.conf`) is installed by
   `pnpm deploy:docker:wsl` at
   `/etc/nginx/sites-enabled/sdkwork/testapikb-knowledgebase.conf`.
3. Visit `http://testapikb.sdkwork.com` (or either other domain) from the
   browser.

### 6.2 Login

The credential-entry login flow (`POST /app/v3/api/auth/registrations`,
`/sessions`) requires a bootstrap Access-Token JWT (`Access-Token` header).
The static portal cannot auto-generate it, so the docker build injects one:

- **Build-time injection** — `scripts/wsl-deploy.sh` generates a bootstrap
  token (signed with the IAM tenant signing master secret,
  `scripts/generate-bootstrap-token.mjs`) and `vite build --mode
  standalone.docker` bakes it into the bundle
  (`process.env.SDKWORK_ACCESS_TOKEN`, vite.config.ts). To pin an explicit
  token, build with `SDKWORK_ACCESS_TOKEN=<token>`.
- **Admin account** — set `SDKWORK_IAM_SUPER_ADMIN_PASSWORD` in `.env`
  (default empty; the IAM bootstrap operator provisions/updates the canonical
  `admin@sdkwork.com` password on startup when set). Then log in as
  `admin@sdkwork.com` from the portal. New self-registered users start
  without knowledgebase write permissions.
- **Manual API smoke** — with a fresh bootstrap token (same secret as
  `.env`'s `SDKWORK_IAM_TENANT_SIGNING_MASTER_SECRET`):
  ```bash
  TOKEN=$(node scripts/generate-bootstrap-token.mjs)
  # register (or use the admin password below)
  curl -X POST http://testapikb.sdkwork.com/app/v3/api/auth/registrations \
    -H "Content-Type: application/json" -H "Access-Token: $TOKEN" \
    -d '{"email":"kbadmin@test.sdkwork.com","password":"Sdkwork@2026Test","confirmPassword":"Sdkwork@2026Test","displayName":"KB Admin"}'
  # login
  curl -X POST http://testapikb.sdkwork.com/app/v3/api/auth/sessions \
    -H "Content-Type: application/json" -H "Access-Token: $TOKEN" \
    -d '{"grantType":"password","email":"admin@sdkwork.com","password":"<SDKWORK_IAM_SUPER_ADMIN_PASSWORD>"}'
  # business API uses the dual-token profile
  curl -X POST http://testapikb.sdkwork.com/app/v3/api/knowledge/spaces \
    -H "Authorization: Bearer <authToken>" -H "Access-Token: <accessToken>" \
    -H "Content-Type: application/json" \
    -d '{"name":"Smoke Space","description":"docker smoke test"}'
  ```

## 7. Upgrading and rollback

1. Rebuild or pull the new image: `pnpm build:container` (or
   `docker pull ghcr.io/...:<version>`).
2. Take a database backup first (see `deployments/runbooks/backup-restore.md`).
3. `docker compose up -d` — the gateway applies pending schema
   baseline/migrations on startup (`SDKWORK_DATABASE_AUTO_MIGRATE=1`).
4. Verify: `docker compose ps`, `curl http://127.0.0.1:3904/readyz`, log in
   through the portal.
5. Rollback: point `KNOWLEDGEBASE_IMAGE` at the previous image tag and
   `docker compose up -d` (restore the database backup if migrations were
   applied).

## 8. Spec compliance notes

- Script naming: `build:container` follows PNPM_SCRIPT_SPEC runtime-target
  naming; `docker:*` public script names are forbidden.
- Identity: `runtimeTarget = "container"`, `deploymentProfile = "standalone"`;
  the image declares `SDKWORK_KNOWLEDGEBASE_DEPLOYMENT_PROFILE` /
  `SDKWORK_KNOWLEDGEBASE_RUNTIME_TARGET` env defaults (DEPLOYMENT_SPEC §5.2).
- Single HTTP bind: the application public ingress is the only listener on the
  application plane (APP_RUNTIME_TOPOLOGY_SPEC §8); bind values come from env,
  never hard-coded ports in source.
- Secrets and configuration are mounted/injected; durable data lives on
  volumes; the image contains examples only (DEPLOYMENT_SPEC §5.4,
  ENVIRONMENT_SPEC §10.6, RUNTIME_DIRECTORY_SPEC §4.5).
- The build records immutable image evidence (digest, package sha256, build
  date) instead of relying on mutable tags (RELEASE_SPEC §4, §5).
